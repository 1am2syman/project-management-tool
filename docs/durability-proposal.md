# Revised durability proposal: one database, commit before acceptance

Status: revision 2 implemented and approved in independent Antigravity Gemini 4 Neon High review (third pass) and then in an independent Claude Opus 5.5 high-effort review of the final source. Linux and Windows verification, including real Windows choosers under an armed foreground lock and large-workspace latency measurements, are complete; the measured interaction delay awaits owner acceptance before rollout. Plan's browser UI, Python backend, existing `plan.db`, project-file formats and native-file safeguards are retained. This supersedes the browser-snapshot proposal. The original planning approval is recorded locally in `.pi/notes/commit-first-durability-review/neon-approval.md`; implementation verification is described in [testing.md](testing.md).

## Product contract

**A completed action becomes accepted only after its SQLite transaction succeeds.** There is one authoritative workspace and one persistence path. No IndexedDB workspace copy, browser recovery journal, offline editing or startup merge/recovery system.

Typing in a cell, changing an unapplied dialog and moving a drag preview are temporary input. Enter, Apply, mouse release, Import, Undo and other substantive commands prepare a candidate; show Pending while committing it. Promote the candidate and update dependent views/undo controls only after acknowledgement. While that action is pending, prevent another substantive command; navigation, reading, copying and diagnostics remain possible when they do not mutate the staged model. A dialog stays open or visibly pending until the outcome is known. An import cannot report success first and save afterward.

On process failure, reopening the same database recovers accepted work. Input never submitted or not confirmed may be lost on browser failure. A transaction can commit even if its HTTP response is lost; restart may therefore contain an action the browser never confirmed. This is stated explicitly rather than solved with a second persistent store.

## Three changes

### 1. One commit boundary for substantive actions

Introduce an asynchronous commit coordinator around the current model. Mutators receive an isolated draft and resolve task/link/log targets by ID inside it; existing closures capturing live objects cannot simply be wrapped and reused. Reuse the scheduler and project representations on the affected candidate, without cloning unrelated projects/history. Candidate construction must suppress `save`, `appState` writes, hooks with external effects and committed-state observers. Gantt frames use a separate preview copy/overlay, never in-place changes to committed tasks. Mouse release submits its final candidate. Named-version previews never replace the live plan.

Deterministic `store.hook`/`amend()` delay adjustments run inside the originating candidate. If a change requires the interactive Delay Record Popover, keep both the triggering change and delay decision staged: Record/Skip submits one transaction and one undo step; Cancel/Escape discards both without any database write. Show the draft preview as unsaved and block unrelated commands while that decision is open. Apply the same outer boundary to overdue-date-plus-reason, `snapshotAgreed`, version restore plus save-current/critical settings, multi-sheet import, template instantiation and file-open plus causes/binding metadata. No nested helper can start another commit.

All mutation entry points use this boundary: task/link edits, dialogs, drags, project creation/deletion/reordering, versions, imports, templates, causes, preferences, Undo/Redo and file-binding metadata. Audit bypasses of `Store.tx()`; disabling a toolbar alone is insufficient. Selection, scroll, active-project choice (`wb.active`) and collapsed rows are cosmetic: they never initiate a workspace write. Keep a local view-active choice separate from the committed workbook's saved active ID. Cosmetic values may piggyback on a substantive candidate, frozen at submission so later scrolling or tab switching cannot alter the exact attempted result. If a selected project is deleted, commit a valid replacement active ID with that deletion. Delay causes are substantive data and use the coordinator.

In SQLite mode remove workspace/template/app-owned setting shadow writes to `localStorage`, the cross-tab storage-event staleness mechanism and automatic adoption of legacy browser projects into a new empty database. Preserve existing legacy bytes for explicit export; never silently erase or adopt them. Read-only export, analysis, version-save preparation and project duplication must read committed/candidate data without calling `store.save()`. A read-only tab never writes. Fast keyboard workflows await the first action before resolving the next action's IDs against the new committed state; they cannot queue old mutating closures.

After a successful database response: adopt the candidate, advance the committed revision, publish UI updates, and resolve the user's action. Never publish a half-applied project or let an older acknowledgement mark newer input saved. No debounce that postpones recording meaningful edits while typing continues. Unsubmitted input gets an unsaved indication.

### 2. Send and write changed data, not the whole workspace history

Keep the current SQLite node store, retained version history, `BEGIN IMMEDIATE`, expected-revision check and `synchronous=FULL`. It already writes changed nodes; the waste is serializing/transmitting the whole workspace and discovering differences by repeatedly flattening/hashing it.

Add one revision-conditional change-set write alongside the full initial load. Use a small fixed structural change format (set/remove/splice) against the persisted JSON representation; accept it only at the backend trust boundary with path/type/size/invariant validation. Apply it atomically with the action's history changes. Avoid replaying domain commands such as “move task one day,” whose results could change with code/time. Persist the final data changes.

For the first implementation, derive changes within the affected project/component using its existing before/after representations. Source tracking may later reduce that scan; a new generic proxy/runtime is not required. Replacing a changed component is allowed where simpler. A one-field edit must not retransmit unrelated projects, templates or old undo entries. Undo can keep the current project-snapshot representation: append only the new snapshot or splice the changed stack, rather than serializing every existing snapshot. Preserve existing undo/redo behavior and retained SQLite history.

Reuse the current versions table and periodic history checkpoints. No second event log, operation-receipt schema or separate snapshot database. The backend change-set contract is:

- `set` replaces an object member or existing array index; `remove` deletes an object member. Deleting/replacing a subtree removes all descendants using escaped path segments and exact separator-bounded ranges with binary ordering, never unescaped SQL `LIKE` prefix matching.
- `splice` is the sole array-resize operation. Update array/container metadata and remap shifted descendant paths to their existing object hashes without decoding or re-hashing untouched blobs. This includes the 150-entry undo cap: dropping the oldest snapshot must not decode/retransmit every retained snapshot. Remaps must handle occupied destination keys safely inside the transaction.
- Capture each touched path's original hash once, and compute net `versions.changes = {path: [before, after]}` after all operations. Cancelled intermediate changes create no history; a true no-op leaves the revision unchanged. Existing historical replay must reconstruct the exact pre/post states.
- Start with a revision check inside `BEGIN IMMEDIATE`. Validate changed subtrees and the relevant container/project headers, including nonempty sheets, unique IDs and a valid saved active project. Use targeted reads of unchanged invariant headers; no full-workspace `inflate/flatten/encode/hash` on ordinary edits. Existing periodic history checkpoint work remains periodic, not per edit.
- Enforce request-size and resulting-workspace-size limits. Maintain one persisted workspace byte count, updated in the same transaction from removed/added logical JSON-node contributions; decode only affected values needed for those contributions. Initialize/check it once during the storage upgrade. Shifted paths retain their byte contributions; object-key/container changes adjust theirs. This small accounting migration replaces the per-edit full-state `json.dumps` size check; it is not an operation receipt or new recovery authority.

Write changed nodes, net history and size accounting atomically, then commit. Full-state bootstrap/import can be a large validated transaction; do not split it into partially accepted steps. Limit the patch dialect to this storage boundary, including strict paths/types/counts and existing JSON/size rules; it is not an unbounded user scripting interface.

The server must actually avoid flattening/hashing unchanged components on its ordinary edit path. Validation may still inspect relationships that span changed records. Scheduling, a new undo snapshot, large project edits and imports can still be proportional to affected project size. This proposal reduces avoidable full-workspace work; it promises neither constant-time editing nor a latency number before measurement. Do not downgrade FULL to Pi's NORMAL setting to make benchmarks look faster.

### 3. Fail clearly; recover from the one database

A validation error leaves the committed state intact and the user's input available for correction. A timeout, connection loss, storage error or revision conflict suspends further substantive commands; preserve the candidate in memory for inspection/copy/download. Do not silently switch storage modes or keep accepting unsaved changes.

Startup reads identity from `/api/health`, acquires the Web Lock for that canonical `dataFile`, and only then reads `/api/projects` and enables edits. Verify the returned identity still matches. SQLite-expected startup treats 404/405, failed load and wrong identity as errors; do not mount an editable default `Store` or fall back to browser storage. A genuinely empty database has `base: null, revision: null`: stage the explicit default/new workspace as one full conditional bootstrap transaction, without reading legacy browser state.

Retry first verifies the response's canonical `dataFile` matches the expected database, then compares parsed state structurally, ignoring object-key order. Wrong identity blocks all writes; a matching numeric revision alone is insufficient. The empty-database base is explicitly null. Keep the exact committed base and exact attempted result in memory; unchanged branches can be shared, and no full-workspace deep clone is required. If disk equals the attempted result, adopt it with the returned revision. If disk still equals the original base at the original revision, allow resubmission of the immutable change set with that expected revision. A delayed original and retry compete under the existing SQLite revision check, so only one can modify that revision. If disk differs, preserve the candidate and require reload after copying/exporting it; never overwrite or automatically merge. Recheck after any further conflict. Never identify success from a revision increment alone or blindly replay a relative patch. Live replacement/restore of the database is unsupported; close all tabs and stop Python before restoring.

The Web Lock makes a second same-profile tab read-only; no heartbeat/lease/takeover protocol. After the writer closes, the second tab reloads, acquires the lock and reads fresh state before editing. Cross-browser/profile concurrent editing is unsupported; the backend's revision check still rejects ordinary conflicts. Reject unsupported locking rather than silently allowing another editor.

Rollout requires closing all editing tabs and restarting Python. The production UI uses only the coordinator. Any retained full-state API for initialization/import must require the same revision/validation rules and cannot be an unnoticed alternate ordinary-save path; incompatible clients must fail visibly. Keep static browser-only previews outside this SQLite production contract.

## Saving files and the original outage

Workspace durability and an explicit `.plan` file save have separate statuses. Keep existing staged/fsynced file replacement, file fingerprints, native-operation journal and unknown-outcome reconciliation. Never rerun an uncertain external file write just because an HTTP call failed.

Add one explicit **Download copy** using the loaded browser's data and Blob download, independent of Python, native dialogs, workspace-save barriers and prior file-operation polling. It neither replaces a connected file nor clears its journal. On failure, offer the pending candidate as an explicitly unsaved copy; unapplied/invalid control contents remain available to copy separately. A `.plan` copy has the existing portable project scope, not a whole-workspace restore promise. Report “Download started,” and ask users to check Downloads. This directly removes the Save-As trap when Python is dead without adding a new workspace recovery format.

Normal Save/Save As explicitly awaits any commit triggered by editor blur/validation before encoding the project, then checks workspace health before initializing the native backend. Encoding reads the resulting committed state. File-token attach/drop changes also pass through the coordinator and existing file-authorization checks. The separate Download copy encoder accepts the frozen staged project and candidate causes without committing them or calling the backend. If the normal action cannot finish, show the error and offer Download copy rather than looping through the unavailable native service. Diagnostic capture stays available on startup and persistence errors. Launcher supervision and durable server logging are availability improvements; they do not create a second data authority or allow new commits while Python is down.

## Costs and limits

The supported workflow is one editor, a local Python service and one SQLite workspace. Every substantive action pays a local HTTP/database round trip. This is an intentional commit boundary, not a promise that latency is invisible. Measure it before rollout. While an action is pending, unfinished new input is outside the accepted-state guarantee. Pending/unsubmitted input is not protected against browser death. The loaded tab can export a copy during an outage; a closed page needs Python restarted to load again. No service worker or automatic offline reopen.

Database/device loss and corruption need an independent backup/restore procedure. SQLite FULL is retained; absolute power-loss guarantees depend on OS/filesystem/hardware behavior. Browser-only authority is a different product choice if accepting work while Python is dead later becomes essential; it is not part of this proposal.

Integration work is real: the current model mutates before save and many commands return synchronously. The coordinator, affected-component change capture and call sites need coordinated changes. No dependency on Pi Durable or Chord is proposed; copy the transaction ordering and cost discipline, not its general agent scheduler.

## Small acceptance suite before shipping

1. Kill Python before commit and after commit/before response; reopen/retry. No half-action or duplicate patch, no false success; a committed-but-unacknowledged action is found safely. Include delayed original requests, no-ops and revision conflicts.
2. Inject SQLite statement/commit failure or disk-full: project state and history roll back together, UI does not adopt the candidate, draft/copy/diagnostics remain usable.
3. Exercise every mutation class, especially imports, Undo/Redo, named-version preview, causes/templates, compound dialogs and drags. No bypass publishes accepted state before commit; initial load never initializes over unavailable storage. Existing history and portable-file tests still pass.
4. Second-tab and conflicting-profile writes refuse safely. Uncertain native file operations retain their evidence while the independent browser copy works with Python stopped. Verify actual Windows chooser behavior using the isolated-profile/OS-chooser procedure.
5. On typical and large Windows workspaces, measure action-to-ack latency, request bytes, nodes visited/hashed/written, and undo/history costs. Compare a small edit while increasing only unrelated projects/history. Ordinary edit payload and server diff work must not grow with unrelated workspace data. Large affected-project work is reported separately. Rollout requires an acceptable measured interaction delay; no numerical target is claimed yet.

## Basis in Pi Durable

Studied official `earendil-works/pi` commit `b882d08f34f8a245c8d3ea8b057759e1b8b2054c`: storage before publication, tracked document deltas with occasional bases, one selected storage backend, explicit deferred presentation state, and stop/reopen on storage failure. Its default SQLite WAL/NORMAL has a weaker power-failure contract than our FULL setting; retain ours. Pi's request-ID admissions and agent-task recovery are not necessary for our conservative read-before-retry path. Its external-effects caveat still applies to native file saves.
